D&D Simulator - LM Studio Application 
Architecture and Setup Guide
A source-aligned implementation plan for persistent game state, fast context routing, 
quest memory, panels, and validated LLM output
Project role: Implementation guide for a local, persistent, single-player text adventure using LM Studio.
CORE PRINCIPLE
The application remembers and validates. The LLM interprets, narrates, and 
proposes.
How this guide fits the existing project
This guide is an implementation companion to the existing Main instructions and Adventure Reference 
Guide. It does not replace their gameplay rules. It explains how to turn their concepts into a desktop application that 
can run for thousands of turns without depending on the LLM to remember the entire campaign.
Terminology alignment: Keep the existing names Game-State Ledger, Rolling Story Summary, and Visual Registry in the 
application. In code, these become database-backed services and records rather than hidden text maintained only inside a chat.
1. Target outcome
 Desktop application. A single-player text adventure with a narrative pane and persistent profile, inventory, 
equipment, skills, quests, map, relationships, journal, settings, and visual panels.
 Local LLM. LM Studio runs the selected model and exposes a local API to the game application.
 Persistent campaign. SQLite stores all authoritative game state, event history, quest summaries, and visual 
references.
 Reliable rules. Deterministic application code performs dice, resource consumption, inventory math, 
progression, deadlines, and validation.
 Fast long-term play. Each turn sends a bounded, relevant snapshot instead of the full campaign transcript.
 Recoverable saves. Every approved state change is recorded, and the game can rebuild panels and resume 
after a restart.

4. LM Studio connection strategy
4.1 Start with the OpenAI-compatible API
LM Studio can run a local server from the Developer tab or with lms server start. The normal local server address is 
http://localhost:1234. For the first version of the game, use the stateless OpenAI-compatible chat endpoint and let 
the application own all conversation and game state.

5.1 Use stable IDs everywhere
 Use IDs such as char_kaelen, npc_edran, quest_forgotten_shrine, loc_keeper_chamber, and item_keeper_core.
 Narration may use display names, but state changes must target stable IDs.
 Never identify an entity only by its position in a panel or by a model-generated name string.
 Keep a unique constraint where duplicates would break the game, such as one active equipment assignment per slot.

8. Turn-by-turn workflow
1. Capture input. The UI sends the player text, selected UI action, campaign ID, and current scene ID to the turn 
controller.
2. Classify the request. Recognize menu commands, out-of-character requests, combat actions, dialogue, travel, 
inventory actions, and ordinary narrative actions.
3. Perform deterministic pre-checks. Reject impossible panel actions before calling the LLM when the 
answer is entirely mechanical.
4. Build a bounded context package. Load only current and relevant state, recent turns, active quest details, 
and a few retrieved memories.
5. Call LM Studio once. Request narration and a structured turn result. Stream narration when the selected 
response format and UI design allow it.
6. Parse and validate. Reject malformed output; validate every state change against current database state.
7. Resolve mechanics. Run dice and deterministic formulas. If the model requested a roll, the application produces 
the real result.
8. Commit atomically. Apply all approved changes in one SQLite transaction and append the event record.
9. Refresh derived state. Update panel views, calculated modifiers, quest display, and active scene snapshot.
10. Maintain memory. Add important event records and refresh summaries only when thresholds are reached.
9. Context builder: prevent replies from slowing over time
The request sent to the model must be rebuilt each turn and kept inside a fixed budget. Old state remains in SQLite and 
is retrieved only when relevant. Do not append every prior version of the panels.

10.1 During the quest
 Append meaningful quest events, not every sentence of dialogue.
 Update objective status immediately after a validated change.
 Keep the quest summary concise and refresh it after major discoveries, battles, decisions, or approximately every 10 
meaningful turns.
 Store exact facts separately from the narrative summary so summary wording cannot overwrite canonical state.
10.2 At quest completion or failure
1. Finalize objective states and deadlines.
2. Apply rewards and consequences through deterministic operations.
3. Generate a concise narrative summary from structured quest events.
4. Store permanent world changes, relationship changes, unlocked routes, and unresolved follow-up threads.
5. Move the quest out of the active context set.
6. Add a short quest result to the campaign summary and retain the full event log for search.

13. Rolling Story Summary
 Purpose. Provide the LLM with compressed narrative continuity without replacing canonical records.
 Content. Recent major events, discoveries, important NPC interactions, meaningful decisions, current conflicts, 
unresolved mysteries, and immediate objectives.
 Refresh triggers. Approximately every 10 meaningful turns, after a major battle, quest result, region change, 
relationship change, world-state change, or save.
 Versioning. Keep the newest summary active and preserve older summary versions for debugging and save 
recovery.
 Safety. Generate the summary from committed events. Never apply database state changes merely because a 
summary says something happened.

15. Save, load, repair, and replay
 Use normal SQLite persistence continuously; a save is a named checkpoint, not the first time state is written.
 Store a schema version and migration history with every campaign.
 Before a named save, commit pending changes, refresh the rolling summary, and record active scene and visual 
references.
 For load, open a database transaction, verify schema compatibility and referenced assets, then rebuild all panels 
from state.
 For repair, show the discrepancy, evidence events, proposed correction, and resulting panel changes before 
committing when user confirmation is appropriate.
 Create a replay test that re-applies event operations to a known checkpoint and compares the resulting state 
checksum.
16. Failure handling
Failure Required behavior
LM Studio not running Show a clear connection status, preserve player input, and offer retry 
after the server is available.
Model not loaded List available models or instruct the user to load the configured model; 
do not corrupt the turn.
Timeout or interrupted generation Cancel cleanly; commit no model-proposed state changes.
Malformed JSON Retry once with a repair request or reject the result; never guess 
missing state operations.
Invalid state operation Reject that operation, log the reason, and either continue with valid 
independent operations or retry the turn atomically.
Database failure Roll back the entire turn and retain the previous committed state.
Missing visual asset Mark the visual pending and continue text play; never claim it was 
restored.

17. Security and privacy
 Bind LM Studio to localhost unless network access is intentionally required.
 If the server is exposed beyond localhost, enable authentication and restrict firewall access.
 Store API tokens outside source control and redact them from logs.
 Never expose a generic database-write tool to the model. Expose narrow operations with explicit schemas and 
permissions.
 Treat imported campaign files, mods, and prompts as untrusted input; validate paths and prevent traversal outside 
the campaign asset directory.
 Keep backups before database migrations and before destructive repair operations.
18. Performance plan
Technique Effect
One primary LLM call per narrative turn Avoids cumulative sequential latency.
No LLM call for ordinary panel opens Panels feel immediate.
Fixed context budget Latency and memory usage remain relatively stable across long 
campaigns.

Delta state output The model returns only proposed changes, not every unchanged record.
Indexed local retrieval Finds relevant history without loading full logs.
Streaming narration Improves perceived responsiveness even when total generation time is 
unchanged.

checkpoints.

Model loaded at practical context length Avoids spending VRAM on an advertised maximum that the game 
rarely uses.

21. Definition of a playable minimum version
